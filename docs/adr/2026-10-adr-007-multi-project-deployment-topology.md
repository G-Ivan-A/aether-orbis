## Context

На одном VPS параллельно работают минимум три независимых ИИ-проекта: AetherOrbis, проект
автоматизации БА-процессов и третий проект. ADR-003 рассчитан на один проект с serverless-вычислениями
и VPS только для состояния. Новая вводная противоречит ему по семи пунктам (К-1…К-7 в
[анализе](../analysis/2026-10-22-multi-project-vps-constraints.md#4-конфликты-с-действующими-adr)).

Ключевые ограничения:

- память — несжимаемый ресурс: один проект с headless-браузерами способен исчерпать её для всех;
- ч. 5 ст. 18 152-ФЗ требует первичной записи и хранения ПДн граждан РФ в базах на территории РФ;
  бэкап в РФ при первичной базе за рубежом это требование не выполняет;
- зарубежный хост даёт в 1,5–2 раза больше RAM на рубль, но несёт риск блокировки аккаунта и сложную
  оплату из РФ;
- ADR-004 (accepted) делает потерю derived knowledge катастрофической: восстановление обходом
  дороже хранения и не воспроизводит наблюдение.

Разбор вариантов, бюджет ресурсов и модель угроз гибрида — в
[RFC § Proposal](../rfc/2026-10-multi-project-vps-platform.md#proposal).

## Decision

1. **Топология ступени 0 — один хост, контейнерный проект на проект.** Каждый ИИ-проект —
   отдельно развёртываемый модульный монолит в собственном контейнерном проекте (compose-проект или
   эквивалент) со своей сетью, томами и секретами. Общая платформенная часть (reverse proxy,
   мониторинг, бэкап-агент) не принадлежит ни одному из проектов. Serverless на ступени 0 не
   используется и остаётся опцией для пиковых stateless-шагов.
2. **Юрисдикция ступени 0 — РФ (вариант A RFC).** Основной хост и второе хранилище бэкапов —
   у двух разных провайдеров в РФ. Гибрид C2 — зарубежный хост только для проектов без D2 —
   **заранее одобрен** как ступень 2 по триггерам T-COST / T-CEIL. Гибрид C1 («всё за рубежом +
   шифрованный бэкап в РФ») и нейтральные юрисдикции отклонены для данных класса D2.
3. **Размещение по классам данных.** Каждое хранилище проекта отнесено к классу D0 / D1 / D2 / S
   ([RFC § 1](../rfc/2026-10-multi-project-vps-platform.md#1-классы-данных)); спорный случай
   относится к более строгому классу.
   - S-1. D2 первично хранится только на узле в РФ и **НЕ ДОЛЖЕН** записываться на хост вне РФ — ни в
     базу, ни в кэш, ни в лог, ни в телеметрию.
   - S-2. Обработка D2 вне РФ допускается только после юридической проверки и уведомления
     Роскомнадзора (ст. 12 152-ФЗ); по умолчанию — запрещена.
   - S-3. Шифрование в канале: TLS на всех внешних точках входа, WireGuard между хостами. Нешифрованный
     HTTP допустим только внутри одного хоста во внутренней сети контейнеров.
   - S-4. Шифрование хранения: все бэкапы шифруются **на клиенте** аутентифицированным шифрованием до
     отправки; провайдер хранилища видит только шифртекст. Тома с D2 на хосте вне РФ запрещены (S-1);
     тома с D1 на хосте вне РФ шифруются на уровне диска.
   - S-5. Ключи: отдельный ключ шифрования бэкапа на проект; ключи хранятся у владельца отдельно от
     бэкапов и вне репозитория; учётные данные бэкап-агента дают только дозапись (append-only /
     object lock); удаление — только ключом владельца.
4. **Изоляция ресурсов и прав.**
   - I-1. Жёсткие лимиты cgroup v2 на каждый контейнер: память, CPU, число процессов;
     memswap = memory (контейнеру не предоставляется swap). Сумма лимитов памяти всех контейнеров
     ≤ RAM хоста − резерв ОС; сумма лимитов CPU может превышать число ядер.
   - I-2. Свободный буфер памяти хоста ≥ 1 GB не распределяется по проектам; его убывание — триггер.
   - I-3. Дисковая квота на проект (отдельный том с квотой), ротация логов контейнеров с лимитом
     размера, ограниченный по размеру tmp. Тома Docker по умолчанию квот не имеют — квота
     обязательна.
   - I-4. Сети: внутренняя сеть на проект; хранилища проекта (Qdrant, БД) подключены только к ней и
     не публикуют порты на хост. Межпроектные вызовы идут только через платформенный reverse proxy
     по ADR-008.
   - I-5. Минимальные привилегии: процесс не от root, `no-new-privileges`, сброс capabilities, без
     `privileged`, без host network; сокет Docker **НЕ ДОЛЖЕН** монтироваться в контейнер проекта.
   - I-6. Секреты на проект: проект не видит секретов другого проекта; префикс переменных уникален
     (`AETHER_ORBIS_*` для AetherOrbis); ключи и бюджеты внешних моделей — раздельные, исчерпание
     бюджета одного проекта не блокирует другой.
   - I-7. Платформенные сервисы защищены от OOM-killer сильнее проектов; у каждого контейнера —
     healthcheck и перезапуск с задержкой.
   - I-8. Headless-браузеры живут в worker-контейнере, а не в API-контейнере; число одновременных
     страниц ограничено `workers.concurrency` Runtime Configuration.
   - I-9. Хост: вход по SSH-ключам, межсетевой экран с запретом по умолчанию (наружу открыты только
     80/443 и ограниченный SSH), автоматические обновления безопасности.
   - I-10. Образы собираются из репозитория проекта, версии фиксированы; runtime-данные в образ не
     попадают (ADR-003 п. 5 сохраняется).
5. **Резервное копирование.** Объём бэкапа AetherOrbis — все три измерения ADR-004: acquired
   artifacts, derived knowledge, observation history, а также Research Run. Схема 3-2-1: рабочая
   копия, снапшот провайдера, шифрованная копия во втором хранилище РФ у другого провайдера.
   RPO ≤ 24 ч, RTO ≤ 24 ч. Восстановление одного проекта проверяется ежемесячно, полная пересборка
   хоста — ежеквартально.
6. **Наблюдаемость с первого дня — для триггеров.** Метрики хоста и контейнеров (RAM, CPU, steal,
   iowait, диск, OOM-события, перезапуски) и метрики Job API (время ожидания, очередь, таймауты)
   собираются с первого развёртывания и хранятся ≥ 30 дней. Конкретный стек выбирается в задаче
   реализации по ресурсному лимиту платформы (1 GB). Langfuse self-host откладывается до триггера
   T-OBS: до него телеметрия пишется по
   [`telemetry-contract.md`](../standards/telemetry-contract.md) в собственный sink проекта.
7. **Триггеры масштабирования.** Архитектура эволюционирует по ступеням
   [RFC § 6](../rfc/2026-10-multi-project-vps-platform.md#6-ступени-эволюции) только при
   срабатывании измеримого триггера:

   | ID | Метрика | Порог и окно | Источник | Действие |
   | --- | --- | --- | --- | --- |
   | T-RAM | использование RAM хоста без page cache | p95 > 85 % за 24 ч или буфер I-2 < 1 GB | метрики хоста | ступень 1: вертикальный рост хоста |
   | T-OOM | OOM-kill контейнеров одного проекта | > 3 за 7 дней | события OOM | лимит проекта из буфера; буфера нет — ступень 1 |
   | T-CPU | загрузка CPU хоста | p95 > 70 % за 24 ч | метрики хоста | ступень 1 |
   | T-STEAL | CPU steal | > 10 % в среднем за 1 ч, ≥ 3 раз за 7 дней | метрики хоста | тариф с выделенными ядрами или смена провайдера |
   | T-DISK | заполненность диска или квоты проекта | > 75 % — расширение; > 85 % — алерт | метрики хоста | расширение тома / ступень 1 |
   | T-IO | iowait | > 20 % в течение 1 ч | метрики хоста | более быстрый диск или отдельный том |
   | T-CEIL | следующий вертикальный шаг | недоступен у провайдера или дороже двух хостов половинного размера в 2× | прайс провайдера | ступень 2: второй хост |
   | T-COST | стоимость инфраструктуры | превышение бюджета > 50 % или цена требуемой конфигурации в РФ > 2× эквивалента C2 | ежемесячная сверка | ступень 2 с вариантом C2 для проектов без D2 |
   | T-QUEUE | Job API ([ADR-008](2026-10-adr-008-inter-project-api-contract.md)) | p95 ожидания задания > 5 мин за 24 ч, или > 100 заданий в `ACCEPTED` дольше 1 ч, или > 1 % синхронных таймаутов за сутки, или ≥ 3 пар производитель–потребитель, или событие нужно ≥ 2 потребителям | метрики Job API | брокер сообщений — отдельным ADR |
   | T-WORKERS | воркеры обхода | очередь воркеров упирается в лимит при простаивающем API, или нужно ≥ 2× `workers.concurrency` | метрики Job API и контейнеров | вынос воркеров в отдельный контейнер / хост с собственным лимитом |
   | T-AVAIL | доступность сервиса | < 99 % за месяц два месяца подряд или требование SLA ≥ 99,5 % | внешний health-check | второй хост с переключением |
   | T-ISO | модель доверия | проект обслуживает внешних недоверенных арендаторов или исполняет пользовательский код | решение владельца проекта | отдельная VM / хост |
   | T-GRAPH | граф | выход за пределы одного процесса | ADR-001 Lifecycle | пересмотр ADR-001 п. 2 |
   | T-OBS | телеметрия | нужен UI трассировок или > 1 млн событий в месяц | телеметрия | Langfuse self-host на выделенном ресурсе |
   | T-ORCH | эксплуатация | ≥ 3 хостов или ручной деплой > 1 ч в неделю | учёт времени | ступень 3: лёгкая оркестрация |

   Kubernetes не рассматривается до ступени 3. Появление D2 у проекта на зарубежном хосте — не
   триггер, а нарушение S-1: D2-часть немедленно переносится на узел РФ.
8. **Владелец платформы.** Платформенная часть (хост, прокси, мониторинг, бэкап) описывается вне
   репозиториев проектов-арендаторов. Место — решение фаундера (RFC, Open Questions, вопрос 4). До
   решения AetherOrbis фиксирует только свою сторону: лимиты, классы данных и контракт.

## Decision Drivers

- Изоляция сбоев: OOM или переполнение диска одного проекта не должны останавливать остальные.
- 152-ФЗ: первичная база ПДн в РФ; бэкап и шифрование не заменяют локализацию.
- Восстановимость по ADR-004: derived knowledge невосстановимо повторным обходом.
- Стоимость ступени 0 сопоставима для вариантов A и C2 (разница 700–2 000 ₽/мес), а риски — нет.
- Переносимость: проект, спроектированный по I-1…I-10, переезжает между хостами и юрисдикциями без
  изменения архитектуры.
- Измеримость: решения об эволюции принимаются по метрикам, а не по ощущению.

## Alternatives Considered

| Альтернатива | Почему отклонена |
| --- | --- |
| Гибрид C1: всё на зарубежном VPS + шифрованный бэкап в РФ | бэкап не выполняет ч. 5 ст. 18 для D2; блокировка аккаунта — простой всех проектов |
| Гибрид C2 сразу на ступени 0 | экономия меньше стоимости одного инцидента; требует правки ADR-003 п. 3 и юридической проверки до первого релиза; оставлен ступенью 2 |
| Нейтральная юрисдикция (KZ / AM / NL с оплатой в ₽) | не снимает ни ч. 5 ст. 18, ни ст. 12; нет ценового преимущества |
| Отдельный VPS на каждый проект | ×3 фиксированных расходов без нагрузки, которая это оправдывает; остаётся ступенью 2 |
| Kubernetes / k3s на одном хосте | накладные расходы control plane без выигрыша в изоляции против cgroup |
| Serverless-first по ADR-003 | целевая среда — один VPS; serverless остаётся триггерной опцией |
| Лимиты без квот на диск | переполнение тома одного проекта останавливает Docker и все проекты хоста |

## Consequences

**Положительные**

- Сбой одного проекта локализован его cgroup, сетью и квотой.
- Требование 152-ФЗ выполняется по построению и проверяется по классам данных, а не по ручному
  чек-листу.
- Переход на гибрид, второй хост или брокер — ступени с заранее известными условиями входа.

**Отрицательные и риски**

- Вариант A дороже C2 на 700–2 000 ₽/мес.
- Жёсткие лимиты памяти дают OOM при пике; сбой локализован, а частота OOM — триггер T-OOM.
- Один хост — единая точка отказа; митигируется бэкапом у второго провайдера и RTO ≤ 24 ч.
- Платформа — общая ответственность трёх проектов; без владельца (п. 8) деградирует.

**Совместимость и миграция (Archetype C) — конкретные правки действующих ADR**

| ADR | Положение | Предлагаемая правка | Обоснование |
| --- | --- | --- | --- |
| ADR-003 п. 1 | serverless-first | «Контейнерный сервис на общем хосте по ADR-007; serverless — опция для пиковых stateless-шагов» | К-1: целевая среда — один VPS |
| ADR-003 п. 2 | VPS как fallback и носитель состояния | «Хост — основная среда вычислений и состояния; бюджет ресурсов — ADR-007 п. 4» | К-1, К-5 |
| ADR-003 п. 3 | хранение и обработка — только в РФ | «Размещение по классам данных ADR-007 п. 3: D2 — только в РФ; D0/D1 — ступень 0 в РФ, вне РФ — по триггеру» | К-2: ограничение для ПДн сохраняется, для публичного контента — уточняется |
| ADR-003 п. 4 | 2FA на публичном API | «2FA — для доступа людей; сервисы — per-caller токены / mTLS по ADR-008 п. 6» | К-3 |
| ADR-003, миграция | «сырой материал — единственный источник, требующий бэкапа» | «Бэкапу подлежат все три измерения ADR-004 и Research Run (ADR-007 п. 5)» | К-4: противоречие с принятым ADR-004 |
| ADR-003, таблица стоимости | 2 vCPU / 4 GB | ориентир для узла D2 или одного проекта; общий хост — по RFC § 2 | К-5 |
| ADR-001, observability | Langfuse | «Langfuse — целевой бэкенд по триггеру T-OBS; до него — sink по telemetry-contract» | К-6: Postgres + ClickHouse + Redis + S3 не помещаются в лимит платформы |
| ADR-002 | приоритет RF-моделей | без изменений; ступень 0 в РФ снимает риск зарубежного хоста для вызовов RF-провайдеров | К-7 |
| ADR-004…006 | доменные контракты | без изменений | не затрагиваются |

ADR-003 п. 5 (граница репозиторий / runtime) и п. 6 (секреты `AETHER_ORBIS_*`) сохраняются и
расширяются I-6 и I-10. В настоящем PR правки внесены в ADR-001 и ADR-003 как аннотации; текст
решений меняется только при принятии ADR-007.

**Runtime-валидация.** Перед первым релизом на общем хосте выполняются проверки из раздела
Compliance and Validation; при переходе между ступенями — повторно.

## Compliance and Validation

| Проверка | Как выполняется |
| --- | --- |
| У каждого контейнера есть лимиты памяти, CPU и числа процессов; swap не выдан | инспекция контейнеров в задаче реализации |
| Сумма лимитов памяти ≤ RAM хоста − резерв | проверка при развёртывании |
| OOM одного проекта не затрагивает соседей | искусственный OOM-тест при приёмке платформы |
| Переполнение квоты одного проекта не останавливает остальные | тест заполнения квоты при приёмке |
| Хранилища проекта не опубликованы на хост и не видны другим проектам | сканирование портов и сетей |
| Сокет Docker не смонтирован в контейнеры проектов | инспекция контейнеров |
| Каждое хранилище отнесено к классу; D2 отсутствует вне РФ | реестр хранилищ проекта + проверка региона ресурсов |
| Бэкап зашифрован на клиенте, учётка бэкап-агента без права удаления | попытка удаления от имени агента должна завершаться отказом |
| Восстановление укладывается в RTO ≤ 24 ч | ежемесячная репетиция на одном проекте, ежеквартальная полная |
| Метрики триггеров собираются и хранятся ≥ 30 дней | проверка наличия рядов T-RAM…T-QUEUE |
| Телеметрия не содержит ПДн | тест контракта телеметрии |

## Lifecycle

Пересматривается при срабатывании любого триггера ступени 2 (T-CEIL, T-COST, T-QUEUE, T-WORKERS,
T-ISO, T-AVAIL), при изменении редакции 152-ФЗ, по итогам юридической проверки (RFC, Open
Questions, вопрос 3) и не реже одного раза за фазу роадмапа. Переход в `accepted` — решение
фаундера.
