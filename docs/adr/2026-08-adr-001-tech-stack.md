## Context

AetherOrbis строится по принципу «интеграция готового OSS + адаптация под модели РФ/Китая +
собственный IP». На фазе подготовительного R&D требуется зафиксировать **стартовый набор кандидатов**
по каждому компоненту пайплайна и правило их замены, не превращая это в преждевременную фиксацию
единственной технологии.

Отдельная сложность — хранение графа. В обсуждениях SSOT граф многократно назывался «архитектурной
способностью», а не выбранной БД: неверный ранний выбор здесь дороже, чем отложенный. Версия 0.2
снимает эту отложенность: эксперимент фазы 1 состоялся, и пункт 2 решения содержит выбор,
обоснованный измерениями.

## Decision

1. Компоненты пайплайна собираются из OSS по таблице ниже. Внутренняя реализация компонента
   заменяема, пока она удовлетворяет контракту на границе
   ([`docs/standards/`](../standards/)).

   | Компонент | Стартовый выбор | Резерв |
   | --- | --- | --- |
   | Crawling | Crawl4AI | Playwright напрямую |
   | Извлечение контента | Trafilatura | Jina Reader |
   | LLM-извлечение | ScrapeGraphAI | llm-scraper, LangChain, LlamaIndex |
   | Хранение графа | **Kuzu** (embedded); default фазы 1 — stdlib-адаптер за тем же портом | Neo4j Community |
   | Vector store | Qdrant | Chroma |
   | Оркестрация | LangGraph | n8n, Prefect |
   | Observability | Langfuse | — |
   | API | FastAPI | — |
   | Маршрутизация моделей | LiteLLM | собственный proxy-слой (см. [ADR-002](2026-08-adr-002-model-routing.md)) |

2. **Графовым движком выбран Kuzu** — по результатам эксперимента фазы 1
   ([`docs/analysis/2026-09-10-graph-store-selection.md`](../analysis/2026-09-10-graph-store-selection.md),
   скрипты в [`experiments/graph-store/`](../../experiments/graph-store)). Основание измерено:
   это единственный кандидат, дающий Cypher, пути переменной длины и персистентность **без
   сервера** — одна зависимость, 20.6 MiB, cold start 424 ms против JVM/контейнера у Neo4j и
   сервера с расширением у PostgreSQL + AGE. По скорости Kuzu проигрывает обоим stdlib-кандидатам
   на всех измеренных масштабах (обход 228.3 ms против 1.9 и 13.5 ms на 5183 рёбрах), поэтому он
   выбран как движок для персистентности и языка запросов, а не как ускорение.

   Default фазы 1 остаётся stdlib-адаптером `InMemoryGraphStore`: на всех измеренных объёмах он
   быстрее и не добавляет зависимостей, а Kuzu включается путём к базе, когда нужна
   персистентность. Оба реализуют один порт `GraphStore`, поэтому код и контракты по-прежнему
   пишутся против абстракции «граф», а не против API конкретной БД, и выбор проверяется тестами
   (`tests/test_representations.py`), а не декларацией.
3. **Собственным кодом** остаются: контракты и модель evidence, confidence scoring, три состояния
   связи, YAML-конфигурации направлений, критерии маршрутизации моделей, логика обоих gates,
   телеметрия, Source Intelligence, evaluation.
4. Vector store и graph store подключаются как **параллельные** представления. Цепочка
   «Graph Builder → Vector DB» как обязательная последовательность отклонена.

## Decision Drivers

- Скорость выхода на работающий пайплайн важнее оригинальности реализации сбора.
- Ценность проекта сосредоточена в контрактах и gates, а не в crawling — там переиспользуем чужое.
- Ранняя фиксация графовой БД — самый дорогой из возможных преждевременных выборов.
- Все выбранные компоненты — self-hostable и совместимы с юрисдикционными ограничениями
  ([ADR-003](2026-08-adr-003-infrastructure.md)).
- Замена компонента не должна требовать изменения контрактов.

## Alternatives Considered

| Альтернатива | Почему отклонена |
| --- | --- |
| Писать crawling и извлечение контента самостоятельно | Не создаёт IP, съедает срок MVP, воспроизводит решённую задачу. |
| Взять готовый end-to-end фреймворк «под ключ» и не писать своего | Gates, evidence-модель и состояния неопределённости в готовых фреймворках отсутствуют — это и есть предмет проекта. |
| Neo4j Community как основной движок | Тот же язык запросов, но до первого запроса требует JVM или контейнер и порт bolt — цена, которой фаза 1 не оплачивает ни одной измеренной выгоды. Оставлен резервом на объёмы, не помещающиеся в один процесс. |
| PostgreSQL + Apache AGE как единое хранилище | Требует сервера и расширения ради модели, которую на графах фазы 1 закрывают два stdlib-кандидата (обход 0.0–58.1 ms). |
| Оставить stdlib-адаптеры единственным решением | Они быстрее на измеренных объёмах, но не дают ни языка запросов с путями переменной длины, ни модели property graph; стратегия `expand` увеличивает граф на каждой итерации, и обход обоих stdlib-кандидатов растёт вместе с ним (0.0 → 14.2 ms in-memory, 1.0 → 58.1 ms SQLite). |
| Vector store как обязательное продолжение графа | Смешивает два независимых представления и навязывает лишний шаг. |

## Consequences

**Положительные**

- Работающий сквозной пайплайн достижим на фазе 1 без написания низкоуровневого сбора.
- Замена любого OSS-компонента локализована внутри одного компонента.
- Выбор графового движка сделан на измерениях воспроизводимого эксперимента, а не на предпочтениях.
- Тесты и CI не зависят от движка: default фазы 1 не требует ни одной зависимости.

**Отрицательные и риски**

- Зависимость от чужих релизных циклов и качества извлечения; митигируется резервным кандидатом по
  каждой позиции.
- Риск «слепого доверия OSS-решениям» зафиксирован в SSOT; митигируется обязательной проверкой
  качества извлечения на моделях РФ/Китая на фазе 2.
- Два адаптера одного порта требуют дисциплины: расхождение их поведения ловится только тестами,
  поэтому контрактные тесты прогоняются против обоих (при отсутствии `kuzu` — со `skipTest`).
- Идемпотентная запись в Kuzu выполняется `MERGE` на элемент и дорога: 12.4 s на 512 рёбер и
  128.3 s на 5183; до объёмов, на которых движок включается всерьёз, адаптеру нужен пакетный
  режим записи, сохраняющий идемпотентность на уровне прогона.
- Масштаб, на котором Kuzu опережает stdlib-адаптеры, экспериментом не найден; это открытый вопрос
  фазы 2, а не установленный факт.

**Совместимость и миграция (Archetype C)**

- Совместимость: контракты `docs/standards/*` не зависят от выбранных OSS-компонентов; смена
  компонента — не breaking change для потребителя.
- Миграция: графовые данные пересоздаваемы из Preserved Records повторным прогоном
  (`project_graph(...)` → `index_graph(...)`), поэтому переход stdlib → Kuzu → Neo4j не требует
  миграционного пути и выполняется сменой адаптера в композиции. Ядро остаётся stdlib
  (`tests/test_module_boundaries.py`), `kuzu` живёт в `requirements-dev.txt`, база данных —
  артефакт рантайма и в git не попадает.
- Runtime-валидация: сквозной прогон двух направлений MVP с проверкой контрактов на каждой границе.

## Compliance and Validation

| Проверка | Как выполняется |
| --- | --- |
| Компонент удовлетворяет контракту границы | автотесты контрактов в CI |
| Отсутствие протечки API конкретной БД в контракты | ревью PR, поиск имён драйверов вне слоя доступа |
| Качество извлечения на целевых моделях | evaluation-набор фазы 2 |
| Резервный кандидат актуален | пересмотр при обновлении этого ADR |

## Lifecycle

ADR пересматривается: (1) когда объём графа выведет его за пределы одного процесса — тогда
проверяется резерв Neo4j Community и пересматривается пункт 2; (2) при отказе любого стартового
компонента от поддержки; (3) не реже одного раза за фазу роадмапа.
