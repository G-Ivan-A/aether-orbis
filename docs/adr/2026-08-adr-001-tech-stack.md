## Context

AetherOrbis строится по принципу «интеграция готового OSS + адаптация под модели РФ/Китая +
собственный IP». На фазе подготовительного R&D требуется зафиксировать **стартовый набор кандидатов**
по каждому компоненту пайплайна и правило их замены, не превращая это в преждевременную фиксацию
единственной технологии.

Отдельная сложность — хранение графа. В обсуждениях SSOT граф многократно назывался «архитектурной
способностью», а не выбранной БД: неверный ранний выбор здесь дороже, чем отложенный.

## Decision

1. Компоненты пайплайна собираются из OSS по таблице ниже. Внутренняя реализация компонента
   заменяема, пока она удовлетворяет контракту на границе
   ([`docs/standards/`](../standards/)).

   | Компонент | Стартовый выбор | Резерв |
   | --- | --- | --- |
   | Crawling | Crawl4AI | Playwright напрямую |
   | Извлечение контента | Trafilatura | Jina Reader |
   | LLM-извлечение | ScrapeGraphAI | llm-scraper, LangChain, LlamaIndex |
   | Хранение графа | **не фиксируется**, определяется экспериментом фазы 1 | Kuzu / Neo4j Community / PostgreSQL + расширение / гибрид |
   | Vector store | Qdrant | Chroma |
   | Оркестрация | LangGraph | n8n, Prefect |
   | Observability | Langfuse | — |
   | API | FastAPI | — |
   | Маршрутизация моделей | LiteLLM | собственный proxy-слой (см. [ADR-002](2026-08-adr-002-model-routing.md)) |

2. **Выбор графовой БД откладывается** до эксперимента фазы 1 роадмапа. До эксперимента код и
   контракты пишутся против абстракции «граф», а не против API конкретной БД.
3. **Собственным кодом** остаются: контракты и модель evidence, confidence scoring, три состояния
   связи, YAML-конфигурации направлений, критерии маршрутизации моделей, логика обоих gates,
   телеметрия, Source Intelligence, evaluation.
4. Vector store и graph store подключаются как **параллельные** представления. Цепочка
   «Graph Builder → Vector DB» как обязательная последовательность отклонена.

## Decision Drivers

- Скорость выхода на работающий пайплайн важнее оригинальности реализации сбора.
- Ценность проекта сосредоточена в контрактах и gates, а не в crawling — там переиспользуем чужое.
- Ранняя фиксация графовой БД — самый дорогой из возможных преждевременных выборов.
- Все выбранные компоненты — self-hostable и совместимы с юрисдикционными ограничениями
  ([ADR-003](2026-08-adr-003-infrastructure.md)).
- Замена компонента не должна требовать изменения контрактов.

## Alternatives Considered

| Альтернатива | Почему отклонена |
| --- | --- |
| Писать crawling и извлечение контента самостоятельно | Не создаёт IP, съедает срок MVP, воспроизводит решённую задачу. |
| Взять готовый end-to-end фреймворк «под ключ» и не писать своего | Gates, evidence-модель и состояния неопределённости в готовых фреймворках отсутствуют — это и есть предмет проекта. |
| Сразу зафиксировать Neo4j | Лицензионные и ресурсные ограничения не проверены на реальной нагрузке; выбор откладывается до эксперимента. |
| Сразу зафиксировать PostgreSQL как единое хранилище | Упрощает инфраструктуру, но не проверено на graph-обходах целевой глубины. |
| Vector store как обязательное продолжение графа | Смешивает два независимых представления и навязывает лишний шаг. |

## Consequences

**Положительные**

- Работающий сквозной пайплайн достижим на фазе 1 без написания низкоуровневого сбора.
- Замена любого OSS-компонента локализована внутри одного компонента.
- Эксперимент по графовой БД даёт решение на данных, а не на предпочтениях.

**Отрицательные и риски**

- Зависимость от чужих релизных циклов и качества извлечения; митигируется резервным кандидатом по
  каждой позиции.
- Риск «слепого доверия OSS-решениям» зафиксирован в SSOT; митигируется обязательной проверкой
  качества извлечения на моделях РФ/Китая на фазе 2.
- Отложенный выбор графовой БД требует дисциплины: слой доступа к графу не должен протекать в
  контракты.

**Совместимость и миграция (Archetype C)**

- Совместимость: контракты `docs/standards/*` не зависят от выбранных OSS-компонентов; смена
  компонента — не breaking change для потребителя.
- Миграция: до эксперимента фазы 1 графовые данные считаются пересоздаваемыми из Raw / Source Store,
  поэтому смена графовой БД не требует миграционного пути.
- Runtime-валидация: сквозной прогон двух направлений MVP с проверкой контрактов на каждой границе.

## Compliance and Validation

| Проверка | Как выполняется |
| --- | --- |
| Компонент удовлетворяет контракту границы | автотесты контрактов в CI |
| Отсутствие протечки API конкретной БД в контракты | ревью PR, поиск имён драйверов вне слоя доступа |
| Качество извлечения на целевых моделях | evaluation-набор фазы 2 |
| Резервный кандидат актуален | пересмотр при обновлении этого ADR |

## Lifecycle

ADR пересматривается: (1) по завершении эксперимента с графовой БД на фазе 1 — тогда пункт 2 решения
заменяется явным выбором; (2) при отказе любого стартового компонента от поддержки; (3) не реже
одного раза за фазу роадмапа.
