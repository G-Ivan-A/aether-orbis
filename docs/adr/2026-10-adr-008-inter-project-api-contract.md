## Context

Три независимых проекта на общем хосте ([ADR-007](2026-10-adr-007-multi-project-deployment-topology.md))
начинают обмениваться данными: БА-проект и третий проект могут заказывать у AetherOrbis
исследовательские прогоны, AetherOrbis — потреблять их результаты. На MVP достаточно HTTP внутри
сети контейнеров. Брокер (RabbitMQ / Redis) понадобится позже — по триггеру T-QUEUE ADR-007.

Если сейчас договориться о синхронном «запрос → ответ» или о доступе к чужой базе, переход на брокер
потребует переписать каждого потребителя. Переход становится бесшовным, только если **форма
сообщения, семантика доставки и жизненный цикл задания** одинаковы для HTTP и для брокера, а меняется
лишь адаптер транспорта.

Дополнительные условия:

- Research Run длится минуты (обход, вызовы моделей) — синхронный ответ упирается в таймауты;
- ADR-006 различает исходы `SUFFICIENT` / `PARTIAL` / `ZERO` / `CONFLICT` / `EXHAUSTED`, и `ZERO` —
  валидный результат, а не ошибка; T3.4 требует отличать ошибку от нуля;
- ADR-003 п. 4 требует 2FA на публичном API, но у сервиса нет второго фактора;
- классы данных ADR-007 должны соблюдаться и при межпроектной передаче.

## Decision

1. **Граница проекта — только контракт.** Проекты взаимодействуют исключительно через опубликованный
   API. Общие базы данных, общие тома, чтение чужих хранилищ и импорт кода другого проекта
   **запрещены**. Каждый проект остаётся модульным монолитом; микросервисы внутри проекта не вводятся.
2. **Contract-first.** Проект-поставщик публикует в своём репозитории OpenAPI 3.1 для HTTP и
   AsyncAPI 3.0 для команд и событий; полезная нагрузка описывается JSON Schema (для AetherOrbis —
   рядом с [`configs/schemas/`](../../configs/schemas/)). Контракт меняется в том же PR, что и код.
3. **Асинхронный Job API — модель по умолчанию.** Любая операция, которая может длиться дольше 2 с или
   вызывает модели либо обход, оформляется как задание:

   | Операция | HTTP (ступень 0) | Ответ |
   | --- | --- | --- |
   | создать задание | `POST /v1/{resource}` с заголовком `Idempotency-Key` | `202 Accepted`, `Location: /v1/{resource}/{id}` |
   | узнать состояние | `GET /v1/{resource}/{id}` | состояние, `Retry-After` для опроса, ссылка на результат |
   | отменить | `POST /v1/{resource}/{id}:cancel` | `202 Accepted` |
   | получить результат | `GET /v1/{resource}/{id}/result` | результат или ссылка на артефакт |
   | уведомление о завершении | callback-событие на зарегистрированный URL потребителя, подписанное HMAC с меткой времени | `2xx` от потребителя = доставлено |

   Синхронные `GET` допустимы для чтения ресурсов с ответом ≤ 2 с. Повтор `POST` с тем же
   `Idempotency-Key` возвращает то же задание, а не создаёт новое.
4. **Единый конверт сообщения — CloudEvents 1.0** (structured JSON) для callback-событий сейчас и
   для сообщений брокера потом: `specversion`, `id`, `source`, `type`, `time`, `subject`,
   `datacontenttype`, `dataschema`, `data`. Обязательные расширения: `correlationid`, `causationid`,
   `idempotencykey`, `deadline`, `traceparent` (W3C Trace Context), `dataclass` (класс данных
   ADR-007: `D0` / `D1` / `D2`). Имя типа включает версию:
   `aether-orbis.research-run.completed.v1`.
5. **Жизненный цикл задания отделён от доменного исхода.** Состояния задания: `ACCEPTED` →
   `RUNNING` → `SUCCEEDED` | `FAILED` | `CANCELLED`. Доменный исход ADR-006 — часть результата
   `SUCCEEDED`: `ZERO` — это `SUCCEEDED` с `outcome: ZERO`, **никогда** не `FAILED`. `FAILED`
   означает техническую невозможность выполнить задание. Ошибки HTTP — в формате Problem Details
   (RFC 9457, `application/problem+json`).
6. **Аутентификация.** 2FA (ADR-003 п. 4) сохраняется для доступа людей. Вызовы машина-машина
   аутентифицируются отдельными учётными данными на каждого вызывающего (токен с перечнем разрешённых
   операций, ротация без простоя); между хостами (ступень 2) — дополнительно mTLS поверх WireGuard.
   Аутентификация обязательна и внутри одного хоста: проекты — независимые арендаторы.
7. **Семантика доставки — at-least-once.** Потребитель идемпотентен по `id` / `idempotencykey` и
   хранит отметки обработанных сообщений не меньше окна повторов. Поставщик записывает событие в
   собственный **outbox** в той же транзакции, что и изменение состояния; диспетчер outbox отправляет
   его с экспоненциальной задержкой и джиттером, после исчерпания попыток — в персистентный список
   недоставленных с алертом (на ступени брокера — dead-letter queue).
8. **Транспорт за портом.** Доменный код не импортирует HTTP-клиент или клиент брокера: отправка и
   приём идут через порт транспорта (по образцу `src/aether_orbis/ports.py`) с HTTP-адаптером на
   ступени 0 и адаптером брокера позже. Переход на брокер = замена адаптера и конфигурации, без
   изменения контрактов и потребителей.

   | Понятие Job API | HTTP (ступень 0) | Брокер (по T-QUEUE) |
   | --- | --- | --- |
   | создать задание | `POST` → `202` | публикация команды в очередь `{provider}.{resource}.v1` |
   | уведомление о завершении | callback-событие | событие в exchange / stream `{provider}.events` |
   | идемпотентность | `Idempotency-Key` | `id` сообщения |
   | повторы | диспетчер outbox | повторная доставка брокером |
   | недоставленные | персистентный список + алерт | dead-letter queue |
   | обратное давление | `429` + `Retry-After` | prefetch / параллелизм потребителя |

9. **Версионирование.** Мажорная версия — в пути (`/v1/`) и в имени типа события (`.v1`). Внутри
   мажорной версии допустимы только аддитивные изменения; потребитель игнорирует неизвестные поля.
   Ломающее изменение — новая мажорная версия; предыдущая поддерживается не менее 90 дней или до
   миграции всех известных потребителей. В CI поставщика проверяются контрактные примеры
   потребителей (consumer-driven contract tests).
10. **Ограничения.** Rate limit на вызывающего — на платформенном reverse proxy. Полезная нагрузка
    ≤ 1 MB; крупные артефакты передаются ссылкой на аутентифицированный `GET` поставщика. Вызывающий
    задаёт `deadline`; задание с истёкшим сроком переводится в `CANCELLED`.
11. **Классы данных в контракте.** Каждая операция и тип события объявляют максимальный класс данных.
    Сообщения `D2` маршрутизируются только между узлами в РФ (ADR-007 S-1). Логи вызовов и телеметрия
    не содержат `data` — только конверт.
12. **Выбор брокера откладывается** до триггера T-QUEUE и оформляется отдельным ADR. Кандидат по
    умолчанию — RabbitMQ: нативные dead-letter exchanges, подтверждения, привязка CloudEvents к AMQP.
    Альтернатива — Redis Streams: легче по ресурсам, но dead-letter реализуется вручную.
13. **Применение к AetherOrbis (T3.4).** Research Run — задание: `POST /v1/research-runs` принимает
    Research Specification (ADR-006); Runtime Configuration остаётся у поставщика, вызывающий может
    лишь понизить бюджет в пределах лимитов. Результат `SUCCEEDED` содержит outcome и ссылку на
    Context Package. События: `aether-orbis.research-run.accepted.v1`, `.completed.v1`, `.failed.v1`.

## Decision Drivers

- Бесшовный переход на брокер: меняется адаптер, а не потребители.
- Длительность Research Run несовместима с синхронным ответом.
- Различимость `ZERO` и ошибки (ADR-006, T3.4).
- Независимость проектов: смена схемы хранения одного проекта не ломает другие.
- Комплаенс: класс данных путешествует вместе с сообщением.
- Наблюдаемость сквозных вызовов через `traceparent` и `correlationid`.

## Alternatives Considered

| Альтернатива | Почему отклонена |
| --- | --- |
| Общая БД между проектами | связанность схем; переход на брокер невозможен без переписывания; ломает изоляцию ADR-007 |
| Синхронный REST «запрос → результат» | таймауты на минутных прогонах; переход на брокер меняет модель взаимодействия у всех потребителей |
| gRPC | та же временная связанность плюс бинарная схема и отдельный инструментарий без выигрыша на MVP |
| Брокер с первого дня | лишний stateful-сервис в бюджете ресурсов до появления асинхронной нагрузки |
| Собственный формат конверта | CloudEvents уже задаёт поля и привязки к HTTP и AMQP; свой формат придётся сопровождать |
| GraphQL-шлюз над проектами | центральная точка связанности; не решает асинхронность |

## Consequences

**Положительные**

- Потребитель пишется один раз: смена транспорта его не затрагивает.
- `ZERO`, ошибка и отмена различимы по контракту.
- Межпроектные вызовы трассируются и проверяются контрактными тестами.

**Отрицательные и риски**

- Асинхронная модель сложнее синхронной: нужны outbox, идемпотентность и callback.
- Outbox и список недоставленных — дополнительное состояние проекта; оно входит в бэкап D1.
- Дисциплина версионирования требует контрактных тестов в CI каждого проекта.

**Совместимость и миграция (Archetype C)**

| Артефакт | Предлагаемая правка |
| --- | --- |
| ADR-003 п. 4 | «2FA — для доступа людей; вызовы машина-машина — per-caller учётные данные и mTLS по ADR-008 п. 6» |
| issue #17 (T3.4) | DoD: Job API по п. 3–5 и 13; OpenAPI-описание как артефакт PR; `ZERO` и `FAILED` различимы по контракту |
| issue #18 (T3.5) | DoD: 2FA для людей; сервисные учётные данные для машин; оба пути покрыты тестом авторизации |
| issue #16 (T3.3) | события телеметрии содержат `correlation_id` и `traceparent` межпроектного вызова |
| ADR-004…006 | без изменений; ADR-006 outcome переносится в результат задания без потерь |

## Compliance and Validation

| Проверка | Как выполняется |
| --- | --- |
| OpenAPI / AsyncAPI валидны и соответствуют коду | валидация спецификаций в CI поставщика |
| Повтор `POST` с тем же `Idempotency-Key` не создаёт второе задание | интеграционный тест |
| Повторная доставка события не меняет состояние потребителя | тест идемпотентности потребителя |
| `ZERO` возвращается как `SUCCEEDED` с outcome, а не как ошибка | контрактный тест |
| Вызов без учётных данных отклоняется и внутри хоста | тест авторизации |
| Callback без валидной подписи или с устаревшей меткой отклоняется | тест подписи |
| Сообщение `D2` не уходит на узел вне РФ | тест маршрутизации по `dataclass` |
| Контрактные примеры потребителей проходят против схемы поставщика | consumer-driven contract tests в CI |

## Lifecycle

Пересматривается при срабатывании T-QUEUE (выбор брокера отдельным ADR), при первом ломающем
изменении контракта и при подключении внешнего, не принадлежащего фаундеру, потребителя. Переход в
`accepted` — решение фаундера.
