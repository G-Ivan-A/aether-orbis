## Context

Шаги пайплайна различаются по цене ошибки на порядки. Ошибка извлечения из одного источника стоит
одного повторного вызова; ошибка анализа портит итоговый вывод. При этом объём вызовов обратный:
извлечение выполняется сотни раз, анализ — единицы.

Дополнительное ограничение: доступность API. Из юрисдикции РФ часть провайдеров недоступна или
недоступна стабильно, что делает выбор «лучшей модели вообще» неприменимым.

## Decision

1. Модель выбирается **по роли операции и требуемому качеству, а не по бренду**. Роли операций:

   | Роль | Профиль | Требование |
   | --- | --- | --- |
   | Extraction | cost-sensitive | приемлемое качество при минимальной цене за единицу объёма |
   | Relevance scoring | cost-sensitive | устойчивость оценки, не креативность |
   | Graph building / entity resolution | mid-tier | точность разрешения сущностей |
   | Sufficiency evaluation | mid-tier | калиброванность отказа |
   | Analysis | quality-first | максимальное доступное качество рассуждения |

2. Приоритет провайдеров: **модели с доступным из РФ API** (YandexGPT, GigaChat) и **китайские
   модели** (Qwen, DeepSeek). Прочие провайдеры допустимы, если доступ стабилен и не нарушает
   ограничений [ADR-003](2026-08-adr-003-infrastructure.md).
3. Реализация — слой Model Router поверх LiteLLM; при недостаточности LiteLLM допускается собственный
   proxy-слой. Компоненты пайплайна **НЕ ДОЛЖНЫ** обращаться к провайдерам напрямую.
4. Обязательные приёмы экономии на cost-sensitive ролях: batch API, prompt caching, semantic caching.
5. Каждый вызов модели фиксируется в телеметрии: роль операции, провайдер, модель, токены, стоимость,
   латентность (см. [`telemetry-contract`](../standards/telemetry-contract.md)).
6. Смена модели для роли — изменение конфигурации, а не кода.

## Decision Drivers

- Стоимость пайплайна определяется дешёвыми массовыми вызовами, качество итога — редкими дорогими.
- Доступность API из целевой юрисдикции — жёсткое ограничение, а не предпочтение.
- Качество извлечения на моделях РФ/Китая не проверено — риск зафиксирован в SSOT и требует
  измеримой проверки, а не допущения.
- Привязка к одному провайдеру создаёт единую точку отказа.

## Alternatives Considered

| Альтернатива | Почему отклонена |
| --- | --- |
| Одна сильная модель на все шаги | Стоимость извлечения растёт кратно без выигрыша в итоговом качестве. |
| Одна дешёвая модель на все шаги | Деградирует анализ — шаг, ради которого собран весь контекст. |
| Жёсткая привязка к одному провайдеру | Единая точка отказа, риск потери доступа к API. |
| Выбор модели по бренду / бенчмаркам общего назначения | Бенчмарки не отражают качество на конкретной роли и конкретном домене. |
| Прямые вызовы провайдеров из компонентов | Делает смену модели изменением кода и ломает телеметрию. |

## Consequences

**Положительные**

- Стоимость прогона управляется настройкой, а не переписыванием.
- Провайдер заменяется без изменения компонентов.
- Телеметрия даёт фактическую цену каждой роли, а не общий счёт.

**Отрицательные и риски**

- Дополнительный слой абстракции и его отказы; митигируется fallback-цепочкой моделей на роль.
- Разное качество structured output у провайдеров РФ/Китая; митигируется валидацией по контракту
  извлечения и повтором вызова при невалидном ответе.
- Semantic caching может вернуть устаревший результат; кэш инвалидируется по `retrieved_at` источника.

**Совместимость и миграция (Archetype C)**

- Совместимость: контракт извлечения не зависит от провайдера — смена модели не меняет форму данных.
- Миграция: при смене модели для роли ранее извлечённые данные не переизвлекаются автоматически;
  переизвлечение запускается явно из Raw / Source Store.
- Runtime-валидация: evaluation-набор по каждой роли перед вводом новой модели в конфигурацию.

## Compliance and Validation

| Проверка | Как выполняется |
| --- | --- |
| Отсутствие прямых вызовов провайдеров вне Router | ревью PR и линт-правило на импорты SDK |
| Каждый вызов имеет запись телеметрии с ролью операции | контрактный тест телеметрии |
| Новая модель прошла evaluation на своей роли | артефакт evaluation в PR |
| Cost-sensitive роли используют кэширование и batch | проверка конфигурации в CI |

## Lifecycle

Пересматривается при появлении нового доступного провайдера, при изменении доступности API из РФ, а
также по результатам evaluation фазы 2 роадмапа.
