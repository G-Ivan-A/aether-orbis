# AetherOrbis — Vision

## Миссия

Дать исследователю и аналитической системе **проверяемый контекст вместо правдоподобного текста**.

AetherOrbis собирает внешние источники, извлекает из них структурированные данные с сохранением
происхождения (provenance), оценивает релевантность и достаточность собранного материала и передаёт
результат аналитическому компоненту через формализованный контракт. Если материала недостаточно,
система обязана сказать об этом явно, а не компенсировать пробел домыслом модели.

## Цель

Каноническая формулировка BUILD-01:

> Создать минимальную, но архитектурно полную систему Web Knowledge Acquisition, которая приобретает
> внешние источники, извлекает структурированные данные с сохранением происхождения, оценивает
> релевантность и качество, сохраняет полный исследованный материал, формирует достаточный контекст
> для последующего рассуждения и предоставляет его аналитическому компоненту через формализованный
> контракт.

Ключевые слова формулировки и их смысл:

| Слово | Что оно обязывает сделать |
| --- | --- |
| приобретает | сбор источников — управляемый процесс с конфигурацией, а не разовый скрипт |
| происхождение | каждое утверждение ссылается на источник и фрагмент |
| релевантность и качество | между сбором и анализом стоит явный gate |
| сохраняет полный материал | отброшенные источники не исчезают, а становятся метаданными |
| достаточный контекст | перед анализом проверяется достаточность, а не только наличие данных |
| формализованный контракт | граница между компонентами описана схемой, а не соглашением «по факту» |

## Проблема

Типовой pipeline «спарсили → закинули в LLM → получили вывод» ломается в трёх местах:

1. **Нет провенанса.** Вывод невозможно проверить: неизвестно, из какого фрагмента какого источника
   он получен.
2. **Нет gate релевантности.** В дорогую аналитическую модель уходит весь собранный шум, и стоимость
   растёт линейно по объёму сбора, а не по объёму полезного сигнала.
3. **Нет gate достаточности.** Модель, получив неполный контекст, не отказывается отвечать — она
   достраивает недостающее. Это и есть основной механизм галлюцинации в исследовательских задачах.

## Что AetherOrbis делает иначе

- **Evidence-backed extraction.** Утверждение без `evidence` и `confidence` не проходит контракт
  извлечения (см. [`docs/standards/extraction-contract.md`](standards/extraction-contract.md)).
- **Три состояния связи.** `OBSERVED` / `NOT_OBSERVED` / `UNCERTAIN`. «Связь не наблюдалась» — это не
  «связи не существует», и система не имеет права схлопывать одно в другое.
- **Relevance/Quality Gate.** Нерелевантный источник не удаляется: он сохраняется как метаданные,
  краткое summary и причина отбраковки. «Сейчас бесполезно» ≠ «никогда не существовало».
- **Sufficiency Gate.** Если контекста не хватает — система расширяет сбор или возвращает явный
  `ZERO` (недостаточно доказательств). Это ключевой элемент IP проекта.
- **Экономика по ролям операций.** Извлечение — дешёвые модели, анализ — сильные модели. Стоимость
  привязана к ценности шага, а не к объёму трафика.

## Позиционирование в экосистеме

AetherOrbis — **Spoke-репозиторий** экосистемы
[hybrid-Intelligence-lab](https://github.com/G-Ivan-A/hybrid-Intelligence-lab) (далее — Хаб).

| Слой | Кто | Ответственность |
| --- | --- | --- |
| Hub | [hybrid-Intelligence-lab](https://github.com/G-Ivan-A/hybrid-Intelligence-lab) | стандарты, governance, методология, шаблоны артефактов |
| Spoke | AetherOrbis | продукт: acquisition-пайплайн, контракты данных, runtime |
| Потребитель | аналитические компоненты и исследовательские практики Хаба | рассуждение поверх поставленного контекста |

AetherOrbis **наследует** governance Хаба и не дублирует его: frontmatter-контракт, правила
именования файлов, структура ADR и структура контрактов взяты из стандартов Хаба напрямую.

### Границы ответственности (что AetherOrbis не делает)

- Не является аналитической системой. Он **готовит** контекст, но не делает выводов по предметной
  области.
- Не является поисковой системой общего назначения. Сбор идёт по сконфигурированным направлениям.
- Не является HTML-парсером. «Парсер» здесь — многомодульный компонент приобретения и структурирования
  данных, а не извлекатель тегов.
- Не строит граф внутри парсера. Решение о том, что становится ребром графа, принимает исключительно
  Graph Builder.

## Метрики успеха (MVP)

| Метрика | Целевое значение MVP |
| --- | --- |
| Направлений исследования на одной кодовой базе | 2, добавляемых YAML-конфигом без изменения кода модулей |
| Доля claims с валидным `evidence` | 100 % (иначе запись не проходит контракт) |
| Отброшенные источники, сохранённые как метаданные | 100 % |
| Явный `ZERO` вместо додумывания при нехватке контекста | обязателен, покрыт тестом |
| Телеметрия по каждому переходу пайплайна | включена в MVP, а не после него |

## Принципы

1. **MVP ≠ простой.** Минимален объём, а не архитектурная полнота.
2. **Интеграция + адаптация + собственный IP.** Готовое OSS берём для сбора и хранения, свой код
   пишем там, где живёт ценность: контракты, confidence, gates, телеметрия, Source Intelligence.
3. **Границы компонентов жёсткие.** Parser ≠ Graph Builder ≠ Analysis.
4. **Граф и вектор — параллельные представления**, а не последовательность.
5. **Репозиторий не хранит runtime-данные.** Базы, секреты и артефакты прогонов живут вне git.
