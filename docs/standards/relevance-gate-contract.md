# Контракт Relevance / Quality Gate

Нормативная лексика по RFC 2119 / BCP 14: **ДОЛЖНО** (MUST), **НЕ ДОЛЖНО** (MUST NOT),
**СЛЕДУЕТ** (SHOULD), **НЕ СЛЕДУЕТ** (SHOULD NOT), **МОЖНО** (MAY).
Термины определены в [`glossary.md`](glossary.md) и здесь не переопределяются.

## Стороны и область

| Сторона | Роль |
| --- | --- |
| Поставщик | Relevance / Quality Gate |
| Потребитель | Graph / Context Builder, Source Intelligence |
| Вход | `ExtractionResult` ([extraction-contract](extraction-contract.md)) |
| Владелец контракта | G-Ivan-A |

**Область:** критерии отбора, форма решения и обязательное сохранение отброшенного материала.

**Вне области:** сбор источников, форма извлечения, оценка достаточности итогового контекста
([sufficiency-gate-contract](sufficiency-gate-contract.md)).

## Обязательства

### O-1. Управление конфигурацией

Критерии релевантности **ДОЛЖНЫ** задаваться YAML-конфигурацией направления
(`configs/directions/<direction>/research-profile.yaml`). Добавление направления **НЕ ДОЛЖНО**
требовать изменения кода модулей.

### O-2. Базовый набор критериев

Профиль направления **ДОЛЖЕН** определять критерии из набора ниже; расширение набора **МОЖНО**
выполнять в профиле.

| Критерий | Что оценивает |
| --- | --- |
| `source_authority` | авторитетность и происхождение источника |
| `technical_specificity` | конкретность, наличие деталей вместо общих формулировок |
| `evidence_presence` | наличие подтверждающих фрагментов, а не заявлений |
| `novelty` | новизна относительно уже накопленного материала направления |
| `applicability` | применимость к вопросу направления |

### O-3. Форма решения

Gate **ДОЛЖЕН** возвращать `RelevanceDecision` с полями `decision` ∈ {`relevant`, `not_relevant`},
`score`, `criteria_scores`, `threshold`, `reason`, `decided_at`.

### O-4. Сохранение отброшенного

При `not_relevant` gate **ДОЛЖЕН** сохранить в Source Intelligence: метаданные источника, краткое
summary и `reason`. Удаление отброшенного источника **НЕ ДОЛЖНО** выполняться.

### O-5. Неизменность содержимого

Gate **НЕ ДОЛЖЕН** изменять `claims`, `entities`, `relations` или их `confidence`. Он принимает
решение о материале, но не редактирует его.

### O-6. Объяснимость

`reason` **ДОЛЖЕН** содержать ссылку на критерии, определившие решение. Решение без объяснения
**НЕ ДОЛЖНО** записываться.

### O-7. Пороги

Пороговое значение **ДОЛЖНО** задаваться в профиле направления. Значение по умолчанию **НЕ ДОЛЖНО**
быть зашито в код без возможности переопределения.

### O-8. Идемпотентность

Повторная оценка того же входа при неизменной конфигурации **ДОЛЖНА** давать то же решение;
недетерминизм модели компенсируется фиксированными параметрами вызова.

### O-9. Телеметрия

Каждое решение **ДОЛЖНО** порождать запись телеметрии с `score`, `decision` и стоимостью вызова.

### O-10. Точка human-in-the-loop

Gate **ДОЛЖЕН** предоставлять точку вмешательства человека. В MVP она реализуется заглушкой:
решение принимается автоматически, событие логируется как `hitl: skipped`.

## Конфигурация

```yaml
research_profile:
  topic: task-processing
  relevance_criteria:
    - source_authority
    - technical_specificity
    - evidence_presence
    - novelty
    - applicability
  threshold: 0.62
  weights:
    source_authority: 0.20
    technical_specificity: 0.25
    evidence_presence: 0.30
    novelty: 0.10
    applicability: 0.15
```

## Логика отбора

1. Каждый критерий оценивается в `0.0`–`1.0`.
2. Итоговый `score` — взвешенная сумма по `weights`; сумма весов **ДОЛЖНА** равняться `1.0`.
3. `score >= threshold` → `relevant`; иначе → `not_relevant`.
4. При `not_relevant` формируется summary и запись в Source Intelligence.
5. Ожидаемое соотношение на типовом прогоне: из ~100 источников ~10 проходят gate полностью,
   ~90 сохраняются как метаданные.

## Definition of Done / критерии соответствия

| Критерий | Проверка |
| --- | --- |
| Новое направление добавляется только YAML-конфигом | тест: прогон второго направления без изменений кода |
| Сумма весов равна `1.0` | валидация конфигурации в CI |
| 100 % отброшенных источников имеют запись в Source Intelligence | контрактный тест |
| Каждое решение содержит непустой `reason` | контрактный тест |
| Содержимое `ExtractionResult` не изменено gate | сравнение хэшей до и после |
| Повторный прогон даёт то же решение | тест идемпотентности |

## Эскалация и исключения

1. **Все источники отброшены.** Gate **ДОЛЖЕН** передать управление механизму расширения сбора и
   зафиксировать событие `all_sources_rejected`; понижение порога «на лету» **НЕ ДОЛЖНО**
   выполняться автоматически.
2. **Отсутствует критерий из профиля.** Прогон завершается ошибкой конфигурации; подстановка
   значения по умолчанию **НЕ ДОЛЖНА** происходить молча.
3. **Пересмотр порога.** Выполняется изменением профиля направления в PR с обоснованием.
4. **Ручное переопределение решения.** Допустимо через точку human-in-the-loop; фиксируется в
   телеметрии как `hitl: override` с автором решения.

## Обоснование и контекст

Gate существует не ради экономии на сборе, а ради экономии токенов дорогой аналитической модели:
широта сбора остаётся высокой, узкой становится только воронка в анализ
([ADR-002](../adr/2026-08-adr-002-model-routing.md)).

Требование сохранять отброшенное следует из принципа SSOT v4.3 «не полезно сейчас ≠ никогда не
существовало»: при смене вопроса направления ранее отброшенные 90 источников становятся уже
собранным материалом, а не потерянной работой.

Запрет редактировать содержимое отделяет решение от данных: если gate начнёт править `confidence`,
станет невозможно отличить оценку источника от оценки утверждения.
