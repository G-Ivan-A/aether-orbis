# AetherOrbis — Концепция

Документ описывает **что** система делает: состав компонентов, контракты между ними и логику двух
решающих gates. Как это разложено по слоям и потокам — см. [`docs/architecture.md`](architecture.md).

## 1. Область и предмет

AetherOrbis решает задачу **Web Knowledge Acquisition**: превращение неструктурированных внешних
источников в проверяемый, оценённый по достаточности контекст для аналитического компонента.

Предмет системы — не «страницы», а **утверждения с происхождением** (claims with evidence).

## 2. Пайплайн

```
Sources
  → Ingestion
  → Raw / Source Store
  → Extraction (entities, relations, claims + evidence + confidence)
  → Relevance / Quality Gate
        ├─ нерелевантно → summary + метаданные + запись в БД (материал сохранён)
        └─ релевантно  → дальше
  → Graph / Context Builder   (параллельно: Vector Index)
  → Sufficiency Gate
        ├─ достаточно      → Analysis
        ├─ недостаточно    → расширение сбора / уточняющий запрос → Relevance Gate
        └─ исчерпано       → явный ZERO (insufficient evidence)
  → Analysis → результат / решение / артефакт
```

Телеметрия снимается на **каждом** переходе (см.
[`docs/standards/telemetry-contract.md`](standards/telemetry-contract.md)).

## 3. Компоненты

### 3.1 Ingestion (сбор)

Приобретение источников по конфигурации направления: списки доменов, поисковые запросы, ленты,
ограничения по частоте и глубине. Отвечает за нормализацию и фиксацию `retrieved_at`.

Не делает: извлечение сущностей, оценку релевантности.

### 3.2 Raw / Source Store

Хранит исходный материал (сырой контент и нормализованный текст) и метаданные источника.
Существует, чтобы извлечение можно было воспроизвести или переиграть на другой модели без
повторного обхода сети.

Живёт **вне репозитория** (см. раздел 7).

### 3.3 Extraction (извлечение)

Из нормализованного текста извлекает `entities`, `relations` и `claims`. Каждый элемент, который
может быть использован дальше в рассуждении, обязан нести `evidence` (`source`, `fragment`,
`retrieved_at`) и `confidence`.

Пример формы claim:

```json
{
  "claim": "Компания A запустила продукт B",
  "confidence": 0.91,
  "evidence": {
    "source": "https://example.com/news/123",
    "fragment": "…в марте компания A объявила о запуске продукта B…",
    "retrieved_at": "2026-08-18T09:14:00Z"
  }
}
```

Экономический профиль: **cost-sensitive**. Дешёвые модели, batch API, prompt caching, semantic
caching (см. [ADR-002](adr/2026-08-adr-002-model-routing.md)).

Не делает: построение графа, вынесение аналитических выводов.

### 3.4 Relevance / Quality Gate

Первый решающий переход. Оценивает извлечённый материал по критериям, заданным YAML-конфигом
направления, и принимает одно из двух решений:

- **relevant** — материал идёт в Graph/Context Builder;
- **not_relevant** — материал **не удаляется**: сохраняются метаданные источника, краткое summary и
  причина отбраковки.

Смысл: из 100 источников полностью обрабатываются ~10 релевантных; остальные 90 остаются в
Source Intelligence и доступны для повторного использования при смене вопроса. Экономия направлена
на токены дорогой аналитической модели, а не на широту сбора.

Контракт: [`docs/standards/relevance-gate-contract.md`](standards/relevance-gate-contract.md).

### 3.5 Graph / Context Builder

Единственный компонент, который решает, что становится ребром графа. Собирает связный контекст из
прошедших gate утверждений, разрешает сущности (entity resolution) и присваивает связям одно из трёх
состояний.

Экономический профиль: **mid-tier**.

### 3.6 Vector Index

Параллельное представление того же материала для семантического поиска. Граф и вектор —
**параллельны**, а не последовательны: вектор не является обязательным следствием построения графа.

| Представление | Для чего |
| --- | --- |
| Graph | структура объектов и связей, graph-based reasoning, обход |
| Vector | семантический retrieval, поиск похожего, расширение контекста |

### 3.7 Sufficiency Gate

Второй решающий переход и ключевой элемент IP. Отвечает на вопрос: **хватает ли собранного, чтобы
рассуждать?** — а не «есть ли хоть что-то».

Действия при недостаточности: уточняющий запрос, расширение сбора, повторный проход Relevance Gate;
при исчерпании бюджета/источников — явный `ZERO`.

Контракт: [`docs/standards/sufficiency-gate-contract.md`](standards/sufficiency-gate-contract.md).

### 3.8 Analysis

Потребитель контекста. Получает данные исключительно через формализованный контракт. Экономический
профиль: **quality-first** — сильные модели.

В составе AetherOrbis Analysis присутствует как граница и контракт; сама предметная аналитика — зона
потребляющих компонентов.

### 3.9 Model Router

Выбирает модель по **роли операции и требуемому качеству**, а не по бренду. Приоритет — модели с
доступным из РФ API (YandexGPT, GigaChat) и китайские модели (Qwen, DeepSeek).
См. [ADR-002](adr/2026-08-adr-002-model-routing.md).

### 3.10 Telemetry

Сквозной компонент: стоимость, токены, латентность, confidence по каждому переходу. Обязателен в MVP.

### 3.11 Human-in-the-loop

Архитектурно заложен как точка вмешательства на обоих gates. В MVP — заглушка (решение принимается
автоматически, событие логируется); обязательным gate становится на фазе S2.

## 4. Контракты

| Контракт | Граница, которую он фиксирует |
| --- | --- |
| [extraction-contract](standards/extraction-contract.md) | Extraction → всё, что ниже |
| [relevance-gate-contract](standards/relevance-gate-contract.md) | Extraction → Graph/Context Builder |
| [sufficiency-gate-contract](standards/sufficiency-gate-contract.md) | Context → Analysis |
| [telemetry-contract](standards/telemetry-contract.md) | все компоненты → наблюдаемость |

Контракты — это то, что делает компоненты заменяемыми: любой OSS-инструмент внутри компонента может
быть заменён, пока он удовлетворяет контракту на границе.

## 5. Три состояния связи

| Состояние | Значение |
| --- | --- |
| `OBSERVED` | связь подтверждена извлечённым evidence |
| `NOT_OBSERVED` | связь не найдена в исследованном материале |
| `UNCERTAIN` | данных недостаточно либо они противоречивы |

Состояния сохраняются осознанно. Схлопывание `NOT_OBSERVED` в «связи нет» превращает пробел в
исследовании в ложное отрицательное утверждение — ровно та ошибка, ради устранения которой строится
система.

## 6. Конфигурируемость направлений

Направление исследования задаётся YAML-конфигом; код модулей при добавлении направления не меняется.

```yaml
research_profile:
  topic: task-processing
  relevance_criteria:
    - source_authority
    - technical_specificity
    - evidence_presence
    - novelty
    - applicability
```

В MVP — **два** направления: репутационные технологии (GRA) и анализ практик Хаба (Habr).
Конфиги: [`configs/directions/`](../configs/README.md).

## 7. Граница «репозиторий / runtime»

Репозиторий содержит: структуру, документацию, контракты, YAML-конфигурации, CI.

Репозиторий **НЕ ДОЛЖЕН** содержать: базы данных (graph, vector, реляционные), сырой и извлечённый
контент источников, секреты и ключи API, артефакты прогонов, логи и телеметрию, кэши моделей.

Это зафиксировано в [`.gitignore`](../.gitignore) и в [ADR-003](adr/2026-08-adr-003-infrastructure.md).

## 8. Что берём из OSS, а что пишем сами

| Берём готовое | Пишем сами |
| --- | --- |
| crawling (Crawl4AI), извлечение контента (Trafilatura, Jina Reader) | контракты и модель evidence |
| LLM-извлечение (ScrapeGraphAI, llm-scraper, LangChain, LlamaIndex) | confidence scoring и состояния неопределённости |
| хранение графа (Kuzu, Neo4j Community, PostgreSQL) | YAML-конфигурации направлений |
| vector store (Qdrant, Chroma) | критерии маршрутизации моделей |
| оркестрация (LangGraph, n8n, Prefect) | логика обоих gates |
| observability (Langfuse), API (FastAPI), routing (LiteLLM) | телеметрия, Source Intelligence, evaluation |

Принцип: OSS — стартовая точка, а не обязательство. Компонент заменяется, контракт остаётся.
